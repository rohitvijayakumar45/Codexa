\title{What Does ``N$\times$ Fewer Tokens'' Measure?\\Baselines, Sampling, and Output Form in\\Repository-Navigation Benchmarks}

\author{\IEEEauthorblockN{Anonymous Author(s)}\IEEEauthorblockA{Anonymized for review}}

\maketitle

\begin{abstract}
Repository-graph tools for coding agents are promoted with large token-reduction ratios.
We ask how much such a ratio depends on how it is measured.
We contribute \textsc{NavBench}, a fully automatic, model-free benchmark with three label layers that never treat an evaluated tool as ground truth:
seeded fixtures whose call sites are known by construction,
17 public Python and TypeScript repositories with independently sampled query targets,
and calls observed while running the Python repositories' test suites.
We apply it to two Tree-sitter code-graph tools (one in two versions), ripgrep, and two language servers.
Re-applying our own prototype's earlier benchmark definition to public code reproduces its headline: graph answers are 85$\times$ smaller than the whole files they replace.
The same graph outputs are only 3.0$\times$ smaller than \rg output, and 1.1--2.2$\times$ \emph{larger} than language-server results printed one location per line.
Sampling targets from that prototype's own graph edges raises its answer rate from 44--54\% to 99--100\%; after adjusting for call fan-out and declaration kind, +32 to +42 points remain, whereas for the other graph tool most of the smaller gap is explained by target composition.
On held-out fixture targets that both answer completely, the most complete graph tool returned as many tokens as ripgrep (ratio 1.03, 95\% CI 0.94--1.13) but far fewer wrong candidates (caller precision 0.98 vs.\ 0.35): its advantage was precision, not payload.
We release the harness and data, and recommend that efficiency claims report baseline, sampling frame, output form, completeness, and precision together.
\end{abstract}

\section{Introduction}
Foundation-model coding agents spend much of their context budget locating code~\cite{bai_tokens}, and graph-based navigation tools, typically exposed to the model as MCP tools, promise to answer structural questions such as ``who calls $X$?'' from a pre-built index~\cite{repograph,codexgraph,locagent,codebasememory}.
Such tools are often promoted with a token ratio.
A ratio, however, has three hidden parameters that are not properties of the tool:
the \emph{baseline} (whole files, grep, or a language server),
the \emph{query sample} (often symbols the graph already connects),
and the \emph{output form} (names only, locations, or source).
Every token such a tool returns is placed in the model's context, so measured payload directly shapes the efficiency claims made for agent tooling.

Our starting point was a research prototype developed by the authors, G1, whose own benchmark reported 85.8$\times$ fewer tokens than reading the referencing files, measured on graph-selected symbols. We include G1 as one of the evaluated tools and report its shortcomings.

We ask:
\textbf{Q1} How does the baseline change measured payload ratios?
\textbf{Q2} How does sampling targets independently of the graph change measured coverage and rankings?
\textbf{Q3} Under the same output form, and with labels no evaluated tool produced, which tools reach useful token--quality operating points?

\emph{Contributions:}
(1)~\textsc{NavBench}, an open benchmark harness with three independent label layers, automatic validity gates, and output-form control;
(2)~evidence that, for identical graph outputs, the measured ratio spans more than two orders of magnitude depending on baseline and output form;
(3)~evidence that sampling targets from a tool's own edges overstates that tool's coverage beyond what target composition explains;
(4)~token--recall--precision profiles by call pattern, and recall on runtime-observed calls, for graph, lexical, and language-server retrieval.

\section{Benchmark Design}
\textbf{Tasks.}
T1 (primary): given a target declaration, return its direct call sites. The gold unit is a call expression whose callee statically binds to the target.
T2: given a call site, return the declaration.

\textbf{Layer A: seeded fixtures.}
A generator emits small, executable Python and TypeScript repositories.
Each contains one instance of every pattern:
direct calls; calls through an import alias, a module or namespace attribute, a re-export, or a typed or \texttt{super} receiver; constructor calls; module-level calls; a same-named method on another class; local shadowing; callbacks; string-dispatched calls; decorators or arrow functions; and comment and string distractors.
Half of the fixtures use common, reused names (``ambiguous'').
The generator writes a manifest of every expected declaration and site.
Python fixtures execute, and TypeScript fixtures compile under \texttt{--strict} and run.
For every Python target, the call lines observed at runtime equal the manifest's sites.
This gate caught three manifest omissions before any held-out data existed.
We use 4+4 calibration and 16+16 held-out fixtures: 224 targets, 160 with explicit call sites.

\textbf{Layer B: natural repositories.}
We use 9 Python and 8 TS/JS libraries, selected by fixed criteria before results were observed, plus 3 pilot repositories excluded from all results.
Declarations are enumerated by tools that share no code with any graph: Python \texttt{ast} and the TypeScript compiler API.
\emph{S-ind}, the primary sample, is drawn from a random pool of $\le$300 non-test declarations, stratified by kind and by the language server's call fan-out, with inclusion weights recorded; it has 661 targets.
\emph{S-cond}, a diagnostic sample of 331 targets, is drawn from declarations with $\ge$1 incoming G1 edge, which is the original benchmark's rule; 76 declarations fall in both samples.
Layer B supports agreement, availability, size, and failure rates, but not accuracy.

\textbf{Layer C: runtime-observed calls.}
Each Python repository's full test suite runs under \texttt{sys.monitoring}.
A call counts only when the callee's entry is confirmed, since \texttt{CALL} fires before invocation.
Calls are mapped to the independent index.
We report recall on observed calls, a different population from all calls; unobserved static results are not false positives.

\textbf{Arms.}
\rg with 0 and 3 context lines (bare name);
pyright 1.1.414 and the TypeScript 5.9.3 language service (\texttt{references} at the declaration; its native form is the LSP \texttt{Location} JSON rebuilt from the returned URIs and ranges);
G1 \texttt{find\_references}, and G1's original \texttt{lookup\_symbol}+\texttt{get\_dependencies} pair;
and \cbm~\cite{codebasememory} at v0.5.5, the release its paper evaluates, at v0.5.7, and at current main (commit \texttt{bf93f0b7}).
v0.5.5 and v0.5.7 gave identical answers on every fixture query; on natural code they differed on 5.8\% of queries, no more than v0.5.7 differs from its own re-run (5.3\%), so they share one row (``v0.5.5/7'').
The \cbm versions are queried through persistent MCP sessions; when a tool reports ambiguity, the follow-up call uses the target's qualified name and both calls are counted.

\textbf{Scoring and statistics.}
Returned facts are mapped to call sites (location tools only), enclosing caller declarations, and files.
A returned location credits its enclosing caller; under a strict rule crediting only locations that are themselves gold call sites, recall of \rg and the language servers changed by $\le$0.01 and no contrast changed.
An answer is \emph{complete} when caller-level recall is 1.
Tokens (cl100k) are counted on each tool's native output, a common one-location-per-line form, and a source-enriched form.
An automatic check confirms identical fact sets across forms for every query.
Estimates are repository-macro means with 95\% hierarchical-bootstrap intervals over repositories, then targets.
The primary contrast and a 1.5$\times$ margin were frozen before held-out data.
Post-freeze changes are reported in \S\ref{sec:threats}.

\section{Results}
\subsection{Q1: the baseline determines the ratio}
Fig.~\ref{fig:q1} and Table~\ref{tab:q1} give the ratios.
Applying G1's original definition to the public repositories reproduces its headline: 85.3$\times$ as a repository geometric mean (95\% CI 57.2--126.9; 152.8$\times$ pooled; 328 targets), consistent with the 85.8$\times$ originally reported.
That definition uses graph-conditioned targets, whole files selected by the graph, and the \texttt{lookup}+\texttt{deps} output.
This reproduces G1's own earlier measurement; it neither reproduces nor tests \cbm's agent-level 10$\times$ result, which measures a different workflow.
Against \rg, the \emph{same} outputs are 3.0$\times$ smaller (2.4--4.0).
Output form alone can flip the sign: the language server's results are larger than every graph tool's output as raw JSON, but smaller in the location form (ratios 0.45--0.88).
In an exploratory regression, the \rg/graph ratio rises with the number of occurrences of the target's name in the repository, with an elasticity of $\approx$0.77 (95\% CI 0.69--0.87).
Lexical retrieval is costly mainly for common, ambiguous names.

\subsection{Q2: graph-conditioned sampling overstates coverage}
Table~\ref{tab:q2} compares the two samples.
S-cond is conditioned on G1's edges, which also changes target composition: 9\% of S-cond but 35\% of S-ind targets have no call site according to the language server, and declaration kinds and name frequencies differ.
For those targets an empty answer is correct.
We therefore post-stratify S-cond to S-ind's distribution over repository $\times$ kind $\times$ fan-out bucket (0, 1--2, 3--9, $\ge$10 call sites).
The adjustment removes composition effects: the language server, on which S-cond is not conditioned, shows no adjusted difference.
For G1, the conditioning tool, the answer-rate gap remains large (+32 and +42 points), while its observed-call recall gap shrinks to +0.13 (95\% CIs reaching 0).
For \cbm the adjusted gaps are small (+8 to +9 points; recall +0.08--0.09, CIs including 0): conditioning inflates mainly the coverage of the tool whose edges define the sample.
Independently sampled declarations are often absent from G1: 14\% of S-ind targets are missing.
G1's coverage of non-test declarations is 91--100\% in the Python repositories, but 47--68\% in five of the eight TS/JS repositories.
The causes are unindexed object-literal arrow functions, and same-named nested declarations that collapse into one node (e.g., 303 test-local classes in one repository).

\subsection{Q3: correctness and tokens at matched quality}
Table~\ref{tab:q3} and Fig.~\ref{fig:q3} report the held-out fixtures.
For the primary contrast we compute the geometric-mean token ratio of each arm to \rg over the targets on which \emph{both} are complete.
These subsets differ by arm (n of 160 below); they are conditioned on success and are not globally matched operating points.
A saving counts as meaningful only if the whole interval lies below $1/1.5\approx0.667$.
\begin{itemize}
\item G1 \texttt{find\_references}: 0.35 [0.33, 0.37] (n=64), a saving, but complete on only 40\% of targets, against 80\% for \rg;
\item G1 \texttt{lookup}+\texttt{deps}: 0.65 [0.62, 0.672] (n=64), a 1.5$\times$ point saving whose interval crosses the threshold, so not meaningful;
\item \cbm current: 1.03 [0.94, 1.13] (n=127), no evidence of a substantial saving (this is not an equivalence test); it is the only graph tool as complete as the baselines (89\%);
\item \cbm v0.5.5/7: 0.58 [0.56, 0.62] (n=79), a saving at 49\% completeness;
\item language-server JSON: 1.75 [1.65, 1.85] (n=128), a cost.
\end{itemize}
Over all 160 targets, without conditioning on completeness, \cbm current's ratio is 1.01 [0.93, 1.09], and the less complete arms' ratios fall to 0.33--0.63.
Small outputs coincided with incomplete answers.

Matched recall is not matched quality.
\cbm current and \rg have the same recall and similar tokens, but \cbm returns almost no wrong callers (precision 0.98 vs.\ 0.35; F1 0.95 vs.\ 0.50).
The fixtures plant same-named methods, shadowing locals, and comment and string mentions, so they are deliberately hard for lexical search; we do not measure precision on natural code.
Output form also matters here: in the common one-fact-per-line form, every graph tool needs only 0.24--0.28 of \rg's tokens on the same jointly complete targets.
The forms differ in content, though: graph lines name callers, while \rg lines list every occurrence of the name.
\cbm's native parity with \rg comes from its verbose tree output (160 native vs.\ 19 location-form tokens).

Failures by pattern are as follows.
\rg misses only calls through import aliases.
pyright also misses them; the TypeScript service does not.
Of G1's 240 missed callers (\texttt{lookup}+\texttt{deps}):
96 are wrong resolutions to a same-named local function that shadows the target;
32 are module-level calls, which it never attributes to a caller;
and 112 are relations it does not record (re-exports, TS constructor calls, and typed-receiver or \texttt{super} calls).
Ambiguous names lower G1's recall from 0.73 to 0.53, but leave \cbm current unaffected (0.95 vs.\ 0.94).
\cbm v0.5.5/7 misses the typed-receiver and constructor calls that the current version finds.
In T2 (definition lookup), every arm found every definition.
Only the language server returned exactly one answer (precision 1.00); the other arms returned same-named candidates (precision 0.68--0.76), at 37--98 tokens.

\subsection{Layer C: recall on observed calls}
On 323 Python targets with observed calls, caller recall was:
\rg 0.95 [0.92, 0.98];
language server 0.79 [0.64, 0.90];
G1 0.75 and 0.69;
\cbm 0.70 (current) and 0.64 (v0.5.5/7).
The language server's misses concentrate in repositories that ship \texttt{.pyi} stubs, because pyright binds public-API calls to the stub declarations rather than the implementation. The graph tools' 0.64--0.75 recall is in the range PyCG reports for static Python call graphs ($\approx$0.70~\cite{pycg}). Their position below lexical search is consistent with Codebase-Memory's agent-level comparison against a grep-and-read explorer (83\% vs.\ 92\% answer quality~\cite{codebasememory}).

\section{Recommendations}
\begin{itemize}
\item Report the baseline, and more than one: the same graph outputs measured 0.45$\times$ to 141$\times$.
\item Sample targets independently of the tool under test: sampling from G1's own edges raised its answer rate by 32--42 points even after adjusting for target composition.
\item Count tokens in a common output form, and state what each form contains: names-only outputs carry less information.
\item Report completeness and precision next to tokens: on jointly complete targets, the most complete graph tool saved no tokens over \rg, but was far more precise.
\item Do not equate payload tokens with agent cost. Agent behaviour and prompt caching are out of scope here, and agent-level studies~\cite{codebasememory,xu_lsp} measure something different.
\end{itemize}

\section{Threats to Validity}
\label{sec:threats}
\textbf{Construct.}
Payload tokens are not agent cost~\cite{bai_tokens,weinberger}.
Static possible-target labels encode one semantics.
Caller-level scoring credits any location inside a true caller; a strict variant changes no result.

\textbf{Internal.}
G1 was developed by the authors; to limit bias, every tool is queried through its own interface under one frozen configuration, and G1's failures are reported in full.
After freezing, we found that pyright answers before its workspace is indexed.
We added a readiness wait (0/80 reference sets changed on re-query 30\,s later) and re-ran all Python jobs.
This raised layer-C language-server recall from 0.73 to 0.79 and changed no conclusion; pre-fix results are released.
Also after freezing, and in response to review: we fixed a scoring error that had dropped the 76 S-ind targets also drawn into S-cond (S-ind numbers changed, no conclusion did; both versions are released); we added \cbm v0.5.5 on the frozen targets with the v0.5.7 adapter; and we added four post-hoc analyses (full-workload ratios, output-form contrasts, strict caller credit, post-stratified sampling), labelled as such in the released reports.
\cbm v0.5.x answers for same-named declarations vary between runs (5\% of natural queries; current version 0.4\%).
Before freezing, name-resolution rules were corrected so that tool outputs are not penalised by our own matching.
Unresolved output (0--6\%) still counts against the tool.
Tokens were counted with gpt-tokenizer's bundled cl100k ranks, validated against known token ids.

\textbf{External.}
Fixtures are cleaner than real code.
The repositories are a purposive selection, and only two languages are covered.
Layer C covers only exercised code.
There is no human audit, so accuracy on natural code is not measured.

\section{Related Work}
Code graphs for agents improve repository-level tasks~\cite{repograph,codexgraph,locagent}.
Codebase-Memory~\cite{codebasememory} reports about 10$\times$ fewer agent tokens than an agent using file reading and grep, at somewhat lower answer quality (83\% vs.\ 92\%).
Xu~\cite{xu_lsp} compares semantic and lexical retrieval inside an agent, including task success, output enrichment, and when token savings arise; we instead measure tools without a model, across graph, lexical, and language-server retrieval, against labels no evaluated tool produced, and quantify sampling effects.
CodeNib~\cite{codenib} compares static and live navigation on graph-derived queries.
For agent memory over long conversations, not code, grep often beats vector retrieval~\cite{grep}.
PyCG bounds what static call graphs achieve~\cite{pycg}.
We complement these agent-level studies with a model-free, cross-tool measurement.
